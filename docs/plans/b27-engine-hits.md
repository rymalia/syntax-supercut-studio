# B27: supercut and songify hits through the engine (person-aware, optional cast)

Board row B27. Goal (Ryan, 2026-10-21): every page that makes an edit identifies its clips with the talking-heads engine.
Today `/sentence` and `/film` do; supercut and songify use `hits.ts` on bucket transcripts and know nothing about who
speaks. After B27 a supercut or song can be limited to one person or `people.json` group and to on-screen speech. Each hit
then carries the engine's person and ASD data into logs and the cut list.

## Why not `engine_cli.py grep`

The baton's first idea was to take hits from `grep`. Reading `cmd_grep` rules it out:

- It returns the whole phrase-bank **run** (`start`/`end` of the sentence around the phrase), not the phrase's word times, and a
  supercut cuts on word times.
- It only searches `phrases/bank.json` (admissible runs), so it finds far fewer hits than the transcripts hold.
- Its `person` is the bank's, which carries the misattribution bug filed to Desktop on 2026-10-21 (the bank skips the
  per-shot split that `person_of` applies).
- It has no regex.

## Design: the app matches, the engine attributes

The `talking-heads` bucket transcripts are generated by `build_buckets.py` from the engine's `words/<cid>.json`. The times
are identical, and on `talking-heads` the word indices are too (checked on c85: 1499 words both, word 100 `a` at 30.32 s).
`talking-heads-onscreen` drops words and inserts `|` tokens, so indices don't line up there, but times do.

So matching stays in `hits.ts`: same phrase normalisation, the same JS regex semantics (the regex-suggest feature produces
JS regexes; Python `re` differs, e.g. `(?<name>…)`). A new engine command then annotates each hit by **clip id + time span**:

```
engine_cli.py attribute --spans <file.json> [--cast <id|name> ...]
```

- Input file: `[{"clip": "c85", "words": [[373.08, 373.4, "scotch"], [373.4, 373.9, "bottle"]]}, ...]`. It is a file, not
  argv, because "you know" yields thousands of hits. Each entry lists the matched transcript words' exact
  `[start, end, text]` (`|` tokens left out).
- The engine finds each word in `words(clip)` by exact `start`/`end` (Codex checked all 351 clips in both buckets: the
  times are identical) plus `norm(text)`, keeping the source index `i` for `allowed_word`.
  - Not a time window: the corpus has 425 zero-length words, e.g. c108's off-screen `of` at 107.36–107.36 right after
    an on-screen word, and a ±5 ms window would pull it into the neighbouring hit (Codex plan review).
  - A word that can't be found makes the span `known: false`.
- RESULT `{ok, spans: [...]}`, same order and length as the input. Each span is
  `{known, words, person, persons, onscreen, asd, face_h, in_cast}`:
  - `known: false` (and nothing else) when the clip has no `words/<cid>.json` or no words fall in the span.
  - `person`: `person_of(clip, w.track, w.start)` when every word agrees, else `null`.
  - `persons`: the distinct ids, in word order.
  - `onscreen`: every word `onscreen`.
  - `asd`: the min word `asd`. `face_h`: the min word `face_h`.
  - `in_cast`: present only with `--cast`. True when every word passes `allowed_word(clip, i, allowed)` with
    `allowed = ∪ ids_of(c)`, the same rule casting uses, so names, person ids and bare clip ids all work.
- Unknown cast names are not an error in `ids_of` (a name not in `people.json` becomes a literal id). The app only offers
  names and ids from `/api/engine/people`, so that is acceptable.
  - The engine logs `LOG cast <x> matches no person` when an entry is neither a `people.json` name, nor a clip id in
    `CLIPS`, nor `<clip>/<cluster>` with that cluster in `identities/<clip>.json`.
  - Not `person_counts()`: it only knows clusters with on-screen words.
- Words with `track: null` (about 43,000), and clips with no identities, attribute to the bare clip id. So a cast that
  names a clip id admits that clip's off-screen words. The on-screen filter is separate on purpose; the UI hint says so.
- Per-clip loading is lazy (`words()` and `ident()` already cache), so the cost scales with the clips that have hits.
- Ownership: the engine is Desktop's, but Ryan chose (2026-10-21) to have Code write this command, as with the 10-15
  ingest-tail change. Flow:
  1. Edit `engine/engine_cli.py` in the repo, and get it reviewed.
  2. Check the live `TH_ENGINE_DIR/engine_cli.py` still equals the snapshot, then copy it over.
  3. Add a row to `docs/ENGINE_CONTRACT.md`.
  4. Leave Desktop an inbox note.

  Nothing else in the engine changes.

## App changes

**`text.ts` `Hit`** gains optional `clip?: string` (the transcript stem, set by `collectHits`), `person?: string | null` and
`asd?: number`.

**`hits.ts`**: `collectHits` sets `clip` and keeps the matched words' `[start, end, text]` on the hit (internal field
`words`, dropped after attribution). New `attributeHits(hits, { cast, onscreen, onLog, signal })` in a new
`src/lib/server/engine-hits.ts`:

1. When neither `cast` nor `onscreen` is set and none of the hits' clips match `^c\d+$`, it returns the hits untouched,
   with no engine call (non-engine buckets keep working without the engine).
2. Otherwise it writes the spans to a file in its own `mkdtemp(tmpdir())` dir, removed in `finally`. Neither
   pipeline has a work dir yet at that point: supercut's dry run never makes one, and songify makes it after
   `collectHits`. It then runs `runEngine(['attribute', '--spans', f, ...cast
   flags], onLog, signal)`, and zips the results back.
3. Filters: with `cast`, it keeps `in_cast === true`. With `onscreen`, it keeps `onscreen === true`. Unknown spans are dropped
   when either filter is on and kept otherwise. It logs counts: `attributed N hits: K kept, U not in the engine, C
   other speakers, O off-screen`.
4. It logs per-person counts (top 10) so a dry run shows who says the phrase.
5. When no filter is set and the engine call fails (not cancelled), it logs a warning and returns the hits unannotated, so
   a broken engine never blocks a plain supercut. With a filter set, the failure fails the job.

**Pipelines**:
- `supercut.ts` and `songify.ts` take `cast?: string[] | null` and `onscreen?: boolean`. Both call `attributeHits` right
  after `collectHits`, before grouping, limits, shuffling and the dry run.
- When filtering leaves nothing, the job fails with `No hits found for "<target>" by <cast> (on-screen)`, before any
  grouping or work dir.
- Cut list:
  - When a hit has a `person`, ` · <person> asd <x.xx>` is appended to the end of its existing marker note.
  - Songify's pitch text stays where it is.
  - Clip `name` and the cut list v1 fields are unchanged; no new schema fields.
- The debug overlay (`drawTextFilter(hit.word)`) appends ` · <person>` when set.
- The output filename gets `-<slugify(cast[0])>` after the slug when a cast is set: `tom_hanks` → `tom-hanks`,
  `c85/1` → `c85-1`. For example: `i-dont-know-tom-hanks-supercut-talking-heads-<ts>.mp4`.

**`api/jobs/+server.ts`**: `supercut` and `songify` accept `cast` (reuse `asOptionalCast`) and `onscreen`
(`asOptionalBoolean`). `jobs.ts` passes them through, and the job `params` record them for the panel.

**UI**:
- Extract the cast dialog from `/sentence` into `src/lib/CastPicker.svelte`: the button, the tag, Clear, and the
  `<dialog>` with `PersonGrid`, loading `/api/engine/people` itself. Props: `bind:cast`.
- `/sentence` uses the extracted component with identical behaviour.
- `/supercut` and `/songify` get the picker plus an "On-screen speaker only" checkbox.
- The hint text says cast and on-screen work on the talking-heads buckets only. With other buckets selected, those hits
  aren't in the engine and get dropped (logged).
- Both pages persist nothing new.

## Out of scope / fallback

- Retiring `talking-heads-onscreen` (B8). The on-screen toggle covers it on the `talking-heads` bucket, but the bucket
  stays until B8.
- B8/B9 (per-word `person`/`onscreen` written into bucket transcripts by `build_buckets.py`) is the alternative to this
  design. It needs no engine call per job but blocks on Desktop. If `attribute` proves slow, B8 is the fallback.
- No ASD threshold control. `onscreen` already encodes the engine's speaker-visible decision. A min-ASD slider can follow
  if Ryan wants one.
- `grep`'s run-level output and the phrase-bank misattribution stay Desktop's.
